# Humanization

The final pass applied to any generated prose (achievement points, CV bullets, standup items, 1:1 talking points, goal reviews, Pulse summaries) after the [Writing Constitution](writing-constitution.md) and [Anti-Inflation](anti-inflation.md) layers, and before output. Where those two layers govern *what can be claimed* and *which words/voice to use*, this layer governs *whether the sentence reads like it was written by a person or generated by a template*.

Inspired by the pattern catalogue in [blader/humanizer](https://github.com/blader/humanizer), adapted to ShipLift's own content (career/engineering writing, not general prose) and constrained by ShipLift's evidence rules: humanization is a phrasing pass only. It must never add, remove, or reweight a fact, metric, date, name, or technology that Evidence Engine and Anti-BS Rules already settled.

---

## 1. Core Rule

> Fix sentences that sound generated. Leave sentences that already sound natural alone.

This is a **minimum-necessary-intervention** pass, not a rewrite-everything pass. A point that already reads like something a senior engineer would say stays untouched.

Humanization never overrides Anti-BS Rules or the Writing Constitution — if a fix would require inventing, softening, or dropping evidence to sound smoother, don't make the fix.

---

## 2. Patterns to Reduce

### A. Fake contrasts

```
❌ It's not just faster tests — it's faster releases.
❌ This isn't about refactoring. It's about maintainability.
✓  Faster tests shortened the release cycle.
```

Keep a contrast only if both halves carry real information the reader needs.

### B. Generic dramatic conclusions

```
❌ And that's where the real impact shows.
❌ This was the key improvement.
```

If a closing sentence adds no new fact, delete it. End on the last concrete point instead.

### C. Staged introductions

```
❌ Here's what shipped this quarter:
❌ Let's break down the impact:
```

Start directly with the title or the first point.

### D. Generic AI vocabulary

Watch for: `crucial`, `pivotal`, `robust`, `delve`, `landscape`, `showcase`, `highlight`, `valuable`, `intricate`, `fostering`, `testament`, `underscore`, `transformative`, `seamless`, `cutting-edge`, `comprehensive` — on top of the buzzwords already banned in the [Writing Constitution](writing-constitution.md) §3.

Not a blocklist — replace a word only when it's there to sound impressive rather than to say something specific. `comprehensive test suite` with no count is decoration; `comprehensive` describing a suite of 40 named test cases is fine.

### E. Inflated phrasing (style, not fact)

This is distinct from Anti-BS Rules (which catches invented *facts*). Humanization catches a true fact dressed in oversized language:

```
Evidence: Built a React dashboard for internal ops users.

❌ Played a pivotal role in transforming the operations workflow.
✓  Built a React dashboard for internal ops users.
```

Never let a humanization pass increase the strength of a claim — only reduce inflation, never add it back as a "more natural-sounding" exaggeration.

### F. Forced triads

```
❌ improved reliability, performance, and developer experience
   (evidence only supports two of the three)
✓  improved reliability and performance
```

Use exactly as many items as the evidence supports — never pad or trim to hit three.

### G. Excessive em dashes

```
❌ Rebuilt the service in React — reducing maintenance overhead — and cut load time.
✓  Rebuilt the service in React, which reduced maintenance overhead and cut load time.
```

If a user's Pulse entries or provided writing sample naturally use em dashes, preserve that style rather than forcing it out.

### H. Repetitive sentence structure

```
❌ Implemented X. Implemented Y. Implemented Z.
✓  Implemented X, added Y, and refactored Z.
```

Vary structure only where it doesn't cost clarity — a flat list of parallel bullets (e.g. CV bullets) is often *supposed* to be structurally uniform; don't force variation onto a format where uniformity is the convention (see §4).

---

## 3. What Humanization Must Never Touch

Never modify, in the course of a humanization pass:

- numbers, percentages, counts, before/after measurements
- dates, time periods, durations
- URLs, PR/issue references, commit hashes
- company names, product names, team names
- technology, framework, language, and tool names (e.g. don't turn `React` into "a frontend library")
- job titles, role names, certifications, degrees
- markdown structure — headings, bullet/numbered lists, bold/italic, code blocks, inline code
- any word that is itself a job-description or keyword match target (CV/ATS context — see §5)

If a candidate rewrite would touch any of the above, skip that rewrite and leave the sentence as generated.

---

## 4. Per-Command Calibration

ShipLift's existing commands set the scope — there's no separate "content type" system to introduce, the command *is* the content type:

| Command | Tone | Intervention level |
|---|---|---|
| `ShipLift CV` | Precise, keyword-preserving | Light — CV bullets are conventionally uniform and dense with ATS-relevant terms; only fix obviously templated phrasing (§B, §C), never restructure or vary bullet form |
| `ShipLift Quarter` | Senior engineer summarizing to a peer | Medium — full pattern pass from §2 |
| `ShipLift 1:1` | Conversational, reflective | Medium |
| `ShipLift Standup` | Terse, functional | Light — standup items are meant to be short and uniform; don't add variation for its own sake |
| `ShipLift Goals` | Analytical | Light — this is structured evaluation output (SMART scores, evidence lists), not narrative prose; only clean up freeform recommendation/gap text |
| `ShipLift Pulse` | Plain factual restatement | None — Pulse summaries are deliberately a restatement of what the user said (see [Output Templates](../output-templates.md) "Pulse Summary Template"); rewriting them for style risks drifting from what was actually reported |

Default, if a command isn't listed above: medium.

---

## 5. ATS / Keyword Protection (CV-specific)

For `ShipLift CV` output specifically, humanization must not reduce keyword match quality:

- never replace a named technology, language, or framework with a paraphrase (`React` must stay `React`, not "a frontend library")
- never replace role/skill terminology likely sourced from a job description with a synonym
- preserve exact metric phrasing already validated by [Metrics](../metrics.md) — humanize the surrounding sentence, not the number or its unit

When in doubt on a CV bullet, prefer leaving the sentence as generated over risking a keyword.

---

## 6. Process

1. Generate the achievement/points/summary normally, following the command's existing pipeline (Evidence Engine → Anti-Inflation → Achievement Generator → command-specific template).
2. Before final output, re-read each generated sentence against §2. Flag only sentences that match a pattern.
3. Rewrite flagged sentences only, using the calibration in §4 for that command.
4. Re-check every rewritten sentence against §3 (preserved content) and against the [Anti-BS Rules](../anti-bs-rules.md) — a rewrite must express the exact same claim as before, not a stronger or weaker one.
5. If a rewrite can't be made without risking §3 or the Anti-BS Rules, discard the rewrite and keep the original sentence. A humanization pass that would corrupt content is worse than no pass at all — correctness always wins over polish.

---

## 7. Validation Checklist

Before finalizing output:

- [ ] No fact, number, date, URL, name, or technology changed by the humanization pass
- [ ] No claim got stronger or weaker than the version Anti-Inflation already approved
- [ ] Markdown/bullet/heading structure unchanged
- [ ] Only sentences that actually matched a §2 pattern were touched
- [ ] Sentences that already sounded natural were left alone
- [ ] `ShipLift Pulse` output was not rewritten (per §4)
- [ ] CV keyword terms untouched (per §5)

---

## 8. Not a Detection-Evasion Tool

This layer exists to make ShipLift's own output read like something a person actually wrote — not to help any output evade AI-detection systems. Evidence-based, non-inflated writing is the goal in its own right, per the [Anti-BS Rules](../anti-bs-rules.md) and [Writing Constitution](writing-constitution.md); humanization is a readability layer on top of already-truthful content, nothing more.
